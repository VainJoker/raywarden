# 备份与恢复边界

备份与恢复由运营者安排。仓库提供构建和部署工作流，完整恢复需要同期的 D1、文件对象和独立的包装密钥。

## 需要一起恢复的内容

- D1：账户验证材料、加密密码项与密钥、设备会话、文件元数据、`jwt_keys`，以及 `d1_migrations` 历史。JWT 签名密钥以 `v1.` 包装格式保存在 D1，同时参与 API Key 包装；恢复时必须保留原行，不能当缓存删除重建。
- 独立的 `KEY_ENCRYPTION_KEY` Worker Secret：解密 D1 根密钥所必需，应与数据库分开安全备份；仓库中的开发值不能用于生产。
- R2 或 KV：附件与 File Send 的实际文件字节。对于这些文件，D1 只有元数据；仅恢复 D1 无法找回文件内容。
- 对应版本的 Worker、配置和前端：恢复的数据结构应与运行代码、迁移链一致。邮件、推送等可选服务的外部 Secrets 不保存在 D1 导出中，需单独保留和配置。全局等价域名和刷新状态可重新获取。

数据库与文件应有能核对的时间点和对应关系。D1 回退到较早状态后，不能假定当前 R2/KV 恰好与之匹配；Worker 版本回滚也不会自动回滚数据库或文件。

已有账户的库若缺失 `jwt_keys`，应用会停止初始化，要求恢复原行或成对导入原始 legacy Secrets；不会自动换一套随机密钥。API Key 新密文使用 `v2.` 标记和用途隔离的派生密钥，旧密文仍可读取；两种格式都依赖原 access secret。新格式 D1 不再直接包含原始签名密钥，但历史原文导出、账户验证与 2FA 材料仍属敏感信息，数据库备份仍需加密保管。

## JWT 包装根密钥与版本回退

加载 JWT 密钥需要正确的 `KEY_ENCRYPTION_KEY`。旧原文行通过条件更新改为 AES-256-GCM 包装，保持原始签名密钥字节，并发请求以已持久化的记录为准。此前导出的原文数据库副本也需要独立加密。

已包装的数据库需要同一外部 Secret 才能读取。错误密钥、篡改、字段交换或混合格式均使加载失败。外部 Secret 的轮换需要单独设计与演练。密钥包装减小 D1 只读泄露的影响，恢复时仍需验证备份来源及完整性。

旧二进制不识别 `v1.` 保存格式，**不能只回滚 Worker 并继续使用包装后的数据库**。应使用识别包装格式的修复版本；确需旧版时，先独立评审并恢复匹配版本、数据库和 Secret，核对备份之后的数据与 R2/KV 文件。滚动切换期间旧实例若读到新包装行可能短暂认证失败，不能用明文回退掩盖这个版本边界。

## 账户验证成本升级的回滚边界

当前账户基线定义逐账户 `password_iterations`，新写入使用至少 `600000` 次与 64 字节随机盐，已记录的更高成本继续保留。客户端 KDF 和 Send 使用独立参数。旧迁移历史需要单独规划数据转移。

**只回滚 Worker 到不识别 `password_iterations` 的旧 Raywarden 不安全。** 旧版本固定按 `100000` 次验证，无法验证已经升级的账户；若它再写入凭据，还可能让 hash 与数据库中保留的成本不匹配。删掉这一列、把成本值改回 `100000` 或只恢复旧 Worker 都不能把一个 `600000` 次的 hash 还原成旧 hash。纯成本升级刻意不修改 `updated_at`、安全戳或账户写入标记，因此这些字段也不能代替备份中的 hash、盐和成本来判断是否已升级。

日常恢复应选择识别逐账户成本的兼容版本，并一起恢复与它匹配的完整数据库备份，包括 `master_password_hash`、`password_salt`、`password_iterations`、`jwt_keys` 和迁移历史。若确需退回不兼容的旧版本，必须另外评审并恢复升级前的完整数据库及其匹配版本；这会丢失备份时间点之后的数据，仍需核对同期 R2/KV 文件。不能把升级前后的几列手工拼接成一个账户。

## 恢复前的最小演练

1. 记录目标环境、代码版本、数据库状态及文件范围，保留原状态；先选择独立数据库和文件存储，不直接覆盖正在使用的库。
2. 在隔离环境恢复 D1，核对实际表结构、`d1_migrations`、关键记录及外键，并确认 Worker 支持备份中的逐账户验证成本。缺失或不可信的历史先单独核对，不盲目重放完整迁移，不吞重复列错误，也不自动补记录，规则见 [迁移说明](../sql/migrations/README.md)。
3. 核对附件和 Send 记录所指向的文件是否存在、大小是否匹配；用指定客户端验证恢复的加密材料仍能使用，不能只以 `/api/alive` 成功判断恢复完成。
4. 记录演练结果、缺失文件和切换条件，再制定实际环境恢复步骤。自动化、备份频率、保留期和恢复耗时均需另行实现与验收。

## 切换文件存储后端

文件元数据和清理作业按对象键关联。Worker 优先选择已绑定的 R2，否则使用 KV。切换前按同一时间点验证 D1 与对象存储，并安排维护窗口。

1. 在原后端仍生效时暂停文件写入、删除和定时清理。核对未完成的上传、暂存记录和清理作业，等待在途请求结束。记录保留的待处理作业及其所属后端。
2. 用 D1 生成已发布对象清单，覆盖附件和已完成的 File Send。优先使用 `storage_key`。旧附件用 `cipher_id/attachment_id`，旧 Send 用 `sends/send_id/file_id`。按清单复制到新后端并验证对象键、字节数和内容摘要。迁入 KV 前核对单对象大小上限。 [运行配置](runtime-config.md)
3. 用独立的 D1 副本和目标绑定试运行，验证旧文件下载、两步上传和失败清理。正式切换前确认旧后端的积压作业已经完成或另有处理安排，避免新后端确认删除后留下旧数据。
4. 发布目标绑定并核对实际产物，通过一组代表性文件验收后恢复写入。保留原后端和同期备份至验收窗口结束。若切换后已有写入，先对齐新增对象和 D1，再决定回退时点。
